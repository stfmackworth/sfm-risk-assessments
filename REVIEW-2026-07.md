# Section B — Bugs (correctness / data loss)

### B1 — "Save to Google Drive" is broken and can never work `P0`
**File:** `src/pages/RAPreview.jsx` (~lines 124–145, `saveToDrive`).
**What's wrong:** The button POSTs directly to `https://api.anthropic.com/v1/messages` from the browser with **no API key** (always a 401, and the API blocks browser CORS anyway), and references a non-existent MCP server (`drivemcp.googleapis.com/mcp/v1`). It reads `VITE_WORKER_URL` into a variable and then never uses it. Every click ends in "Drive failed — retry".
**Failure scenario:** Any user clicks 📂 Save to Google Drive → spinner → error. Feature has never worked.
**Fix (choose one):**
1. **Remove the button** (recommended short-term). "Open as PDF" + browser print-to-PDF already covers the need.
2. Longer-term: route through the Cloudflare Worker (Worker holds a Drive-scoped service account and does the upload). Needs a Worker change — supply the complete Worker file.
**Do NOT** add an Anthropic or Google API key to the client bundle.
**Accept:** No dead button in the preview toolbar; if option 2, an uploaded file appears in the target Drive folder and the returned link opens.

### B2 — Editor → Preview → Back silently discards unsaved work `P0`
**Files:** `src/App.jsx` (~line 56: `if (page === 'preview' && previewRA) return <RAPreview ... onBack={() => setPage('list')} />`) and `src/pages/RAEditor.jsx` (Preview button passes unsaved `local`).
**What's wrong:** Preview from the editor unmounts the editor (top-level early return in `AppShell`), and Preview's Back goes to **the list**, not back to the editor. The editor's unsaved `local` state is destroyed.
**Failure scenario:** Admin spends 20 minutes editing hazards → clicks Preview to check the document → clicks ← Back → lands on the list; all edits gone, no warning.
**Fix:** Track where preview was opened from (e.g. `previewReturn: 'list' | 'edit'` state in `AppShell`). When opened from the editor, Back should return to `page='edit'` **with `activeRA` set to the previewed (unsaved) object** so the editor remounts with the in-progress data (pass the edited RA back into `activeRA` when navigating to preview from the editor). Simplest surgical approach: `onPreview={(r) => { setActiveRA(r); nav('preview', { preview: r }); setPreviewReturn('edit'); }}` and `onBack={() => setPage(previewReturn)}`.
**Accept:** Edit a field → Preview → Back → editor shows the edited (still unsaved) value. From the list, Preview → Back still returns to the list.

### B3 — No unsaved-changes protection at all `P0`
**File:** `src/pages/RAEditor.jsx`.
**What's wrong:** A `dirty` flag exists but is cosmetic (shows "Unsaved changes" text). The ← Back button discards without confirmation; browser refresh/close has no `beforeunload` guard; there is no draft autosave.
**Failure scenario:** Accidental Back click, tab close, or PWA refresh loses all edits.
**Fix (three small parts):**
1. Back button: `if (dirty && !window.confirm('Discard unsaved changes?')) return;`
2. `useEffect` registering `beforeunload` while `dirty` (`e.preventDefault(); e.returnValue = ''`), removed on save/unmount.
3. (Optional, pairs with F8) Autosave `local` to `sessionStorage` keyed by `ra.id`, offer restore on remount.
**Accept:** Dirty editor + Back → confirm dialog. Dirty editor + tab close → browser prompt. Save clears both.

### B4 — Import/Restore is silently undone when Google Sheets is enabled `P0`
**Files:** `src/hooks/useRiskAssessments.js` (`importAssessments` → `patchLocalAssessments` only) and `src/pages/StaffSettings.jsx` (Data & Backup tab).
**What's wrong:** Importing a JSON backup writes **only to localStorage**. On next load, Sheets is the source of truth (`loadAll`), so the imported data is replaced by whatever is in the Sheet. The UI says "restored successfully" and even tells users the Push button is "Only needed once".
**Failure scenario:** James restores last month's backup after a bad edit → sees "✓ 34 assessments restored" → reloads tomorrow → restore has vanished.
**Fix:** In `importAssessments`, when Sheets is enabled, also call `syncToSheets(imported)` (await it, surface failure). Update the success message to say it synced. If Sheets is disabled, current behaviour is fine.
**Accept:** With Sheets enabled: import a backup → hard reload with `?nocache=1` → imported data still present, and the Sheet rows match.

### B5 — Wizard step 3: hazards shown as ticked are silently dropped `P0`
**File:** `src/pages/RAWizard.jsx` — line ~294 (`const on = selectedHazards?.[text] ?? true;`) vs line ~142 (`if (selectedHazards?.[text])`).
**What's wrong:** `selectedHazards` is initialised **once** on first entry to step 3. If the user goes back to step 1/2 and changes category or flags, newly suggested hazards are not in the map. The UI defaults them to **checked** (`?? true`) but `handleConfirm` treats missing keys as **unchecked** — so hazards that look selected never reach the editor. Also, first click on such an item sets it `true`, so clicking appears to do nothing.
**Failure scenario:** Pick "Premises" → Next → Next (step 3 initialised) → Back → also tick "Involves food" → step 3 now shows Food & Allergens all ticked → confirm → none of the food hazards are in the created RA.
**Fix:** Make the two sides consistent and re-initialise on group change. Cleanest: in `enterStep3`, merge — for each currently suggested hazard not yet a key in `selectedHazards`, set it `true` (preserving the user's existing untick decisions). Then change line 294's fallback to `?? false` (map is now always complete for rendered items) or leave `?? true` — with the merge they agree.
**Accept:** Repro above now yields the food hazards in the editor; previously unticked items stay unticked after going back/forward.

### B6 — "Overdue review" stat and filter are dead (always 0) `P0`
**Files:** `src/hooks/useRiskAssessments.js` (load block converts `active`+overdue → `needs_review`; `stats.overdue` counts `active`+overdue) and `src/pages/Dashboard.jsx` / `src/pages/RAList.jsx` (Overdue tile/chip).
**What's wrong:** On every load, overdue active RAs are auto-converted to `needs_review`. `stats.overdue` then counts *active* overdue RAs — which is now an empty set. The Dashboard "Overdue review" tile shows 0 (green) even when reviews are badly overdue, and the RAList "Overdue" chip matches nothing. The genuinely useful signal is hidden inside "Needs review".
**Failure scenario:** 5 assessments blow past their review dates → Dashboard shows "Overdue review: 0" in reassuring green; "Needs review: 5" gives no urgency signal. A trustee glancing at the dashboard is misled.
**Fix (pick one, recommend #1):**
1. Redefine overdue as *status-independent*: `overdue = assessments.filter(a => a.status !== 'archived' && a.reviewDate && isOverdue(a.reviewDate))` and align the RAList `overdue` flag filter the same way (drop the `status === 'active'` condition in both `RAList.isOverdue` usage and `Dashboard.ReviewAlert`).
2. Or stop auto-converting and keep `active` until someone marks it.
Keep tile → filter behaviour consistent (see also W4).
**Accept:** Set an RA's review date to yesterday → reload → Dashboard Overdue tile shows ≥1 (red), clicking it lists that RA, ReviewAlert banner and chip agree.

### B7 — Auto-status change never reaches Google Sheets `P1`
**File:** `src/hooks/useRiskAssessments.js` (load block → `patchLocalAssessments(withStatus)` only).
**What's wrong:** The `active → needs_review` migration persists to localStorage but not Sheets. The Sheet permanently says `active`; every device re-derives the conversion at load; the audit log never records it; anything reading the Sheet directly (e.g. a future email-reminder Worker, Phase 5 item 5) sees stale statuses.
**Fix:** Either write the changed rows back to Sheets after conversion (batch: reuse `syncToSheets`-style clear+update once, guarded so it only fires when `changed`), or implement B6 option 1 (derive overdue at render time, never mutate status automatically) — which makes this moot and is the better design.
**Accept:** After load converts (or derives) statuses, the Sheet and the app agree; no repeated conversion on every device.

### B8 — Save failures are completely silent `P1`
**Files:** `src/utils/storage.js` (every write wrapped in `try/catch` + `console.error`), `src/hooks/useRiskAssessments.js` (`error` state), `src/App.jsx` (never renders `ra.error`).
**What's wrong:** If a Sheets write fails (Worker down, quota, offline), the user sees "Saving…" end normally and believes the save succeeded. localStorage has the data but Sheets doesn't; another device/reload shows old data. The hook's `error` state is set only for thrown errors (storage.js swallows them) and is rendered nowhere.
**Fix:**
1. In `storage.js`, stop swallowing: rethrow after `console.error` (or return a success flag) for `saveAssessment`, `deleteAssessment`, `saveStaff`, `saveSettings`, `saveHazardLibrary`.
2. In the hook, set `error` on failure and add `clearError`.
3. In `App.jsx`, render a dismissible red banner under the nav when `ra.error`: "Cloud save failed — your change is stored on this device only. Retry / Dismiss". Retry = re-attempt the last write (simplest: re-call `saveAssessment(lastRa, assessments)`).
**Accept:** Kill the Worker URL locally (dev override) → save an RA → visible failure banner; restore → retry succeeds and banner clears. Local-only mode (no Sheets) shows no banner.

### B9 — Settings/staff race can overwrite real data with defaults `P1`
**File:** `src/pages/StaffSettings.jsx` (`useState(staff)` / `useState(settings)` initialise once).
**What's wrong:** If the admin opens Staff & Settings before `loadAll()` resolves (slow connection), the page snapshots `DEFAULT_STAFF`/`DEFAULT_SETTINGS` into local state. Pressing Save then writes the defaults over the real Sheet data (staff directory wiped back to TBCs).
**Fix:** Sync local state when props change and the user hasn't edited: `useEffect(() => { if (!dirtyStaff) setLocalStaff(staff); }, [staff])` (same for settings), or simpler — don't render the tabs until `!loading` (pass `loading` down and show a skeleton).
**Accept:** Throttle network → open Settings immediately → real staff appear when load completes; Save never writes defaults unless the user actually typed them.

# Section S — Security & data protection

> Context for junior agents: this is a small church app with one admin. The goal is not
> enterprise hardening; it is (a) don't leak personal data, (b) don't let strangers write
> to the data store, (c) be honest in docs about what the client-side password does.
> S1+S2 share one fix and should be done together as a single piece of work.

### S1 — Cloudflare Worker accepts writes from anyone on the internet `P1`
**Files:** Worker (see `SETUP.md` Part 4 for current source), `src/utils/storage.js` (`sheetsWrite`).
**What's wrong:** The Worker's only protection is a CORS `ALLOWED_ORIGIN` header — which browsers enforce but `curl` ignores. The Worker URL ships inside the public JS bundle. Anyone can extract it and issue `append`/`update`/`clear` operations — including wiping every tab of the Sheet.
**Fix:** Add a shared-secret check to the Worker — but note the secret cannot live in the client bundle (that's public too). Correct minimal design:
1. Worker gains a `POST /login` route: body `{ password }`, compared against a new Worker env var `ADMIN_PASSWORD`; returns a short-lived signed token (HMAC of expiry using a Worker secret).
2. All write operations require `{ token }` in the body; Worker verifies signature + expiry.
3. App: `useAuth.login()` calls the Worker instead of comparing locally (fixes S2 at the same time); stores the token in `sessionStorage`; `sheetsWrite` includes it.
4. `VITE_ADMIN_PASSWORD` GitHub Secret is then removed from the build (it moves to a Worker env var). Update `SETUP.md` accordingly.
Supply the **complete Worker file** when implementing. Keep the `text/plain` no-preflight trick.
**Accept:** `curl` to the Worker without a valid token → 401; app login still works; writes succeed only when logged in; wrong password shows the existing error message.

### S2 — Admin password is extractable from the public bundle `P1`
**File:** `src/hooks/useAuth.jsx` (`import.meta.env.VITE_ADMIN_PASSWORD` inlined at build).
**What's wrong:** The password is a plain string inside the deployed JS (the same way this review recovered the Sheet ID and API key from the live bundle). Client-side comparison is a courtesy gate, not security. Today, extracting it also grants nothing *extra* beyond S1's already-open Worker — but once S1 lands, a bundle-visible password would defeat it.
**Fix:** Solved by S1 step 3 (server-side verification). Until S1 lands, no code change — but add one honest line to `SETUP.md`: "the admin password restricts the UI only; it is recoverable from the bundle by a determined person."
**Accept:** After S1: no `VITE_ADMIN_PASSWORD` reference in the bundle (`grep` the built JS).

### S3 — Staff personal data is publicly readable (GDPR) `P1`
**Files:** Sheet `staff` tab (names, emails, phone numbers); `src/utils/storage.js` (`sheetsRead` with API key).
**What's wrong:** The Sheets API key + Sheet ID are in the public bundle, and the key's HTTP-referrer restriction is spoofable (`curl -H "Referer: …"` works — verified during this session). Anyone can therefore read the `staff` tab: real names, emails, mobile numbers of church staff. That is personal data under UK GDPR being served to the open internet.
**Fix options (in preference order):**
1. **Stop storing email/phone in the Sheet** — the app only *displays* them in Settings; nothing else uses them. Keep name + role; remove the two columns from the UI and `STAFF_COLS` mapping (migration: blank them in the Sheet).
2. Or proxy reads through the Worker with the S1 token for the `staff` range only (public ranges stay key-based).
3. Or accept the risk explicitly — but record that decision in `SETUP.md` and tell the PCC/data-protection lead.
**Accept:** Option 1: `staff!A2:E` contains no emails/phones; app functions unchanged elsewhere. Option 2: unauthenticated read of `staff` range fails, app still shows contacts to logged-in admin.

### S4 — `npm run deploy` publishes a broken, secret-less build `P1`
**File:** `package.json` (`"deploy": "npm run build && gh-pages -d dist"`), dep `gh-pages`.
**What's wrong:** Running it locally builds **without** any `VITE_*` secrets (those exist only in GitHub Actions) and force-pushes that bundle to Pages — deploying an app with no admin login and no Sheets, overwriting the good deploy. One habitual `npm run deploy` breaks production until the next Actions run.
**Fix:** Delete the `deploy` script and the `gh-pages` devDependency. Deployment is push-to-main only.
**Accept:** `npm run deploy` no longer exists; `git push` remains the deploy path.

### S5 — Stored XSS via `generateHTML` (print/PDF document) `P1`
**File:** `src/pages/RAPreview.jsx` — `generateHTML()` interpolates `ra.name`, `hz.hazard`, `hz.existingControls`, etc. into raw HTML without escaping.
**What's wrong:** The on-screen React views are safe (text rendering), but "Open as PDF" builds an HTML string and opens it. Any `<script>`/`<img onerror>` payload stored in a field executes in the viewer's browser. Combined with S1 (anyone can write to the Sheet today), this is a working stored-XSS chain against anyone who opens a share link and clicks Open as PDF.
**Fix:** Add a tiny `esc(s)` helper (`&<>"'` → entities) and wrap **every** `${...}` interpolation of user data in `generateHTML`. No visual change to the printed document.
**Accept:** Set a hazard description to `<img src=x onerror=alert(1)>` → Open as PDF shows the literal text, no alert. Printed layout unchanged for normal data.

# Section A — Accessibility (one coherent work item)

### A1 — Keyboard and screen-reader access is broken for core controls `P2`
**Files:** `RAEditor.jsx` (activity-flag toggles are `div onClick`), `RAWizard.jsx` (flag cards, hazard checkboxes are `div onClick`), all pages (✕ buttons unlabeled), modals (no `role="dialog"`/`aria-modal`).
**What's wrong:** The toggle switches and wizard checkboxes cannot be operated by keyboard at all, and announce nothing to screen readers. For a church aiming at broad volunteer access this matters.
**Fix (single pass):**
1. Toggles → `<button role="switch" aria-checked={on} onKeyDown={space/enter}>` (or a visually-hidden `<input type="checkbox">` wrapper).
2. Wizard hazard items → real `<input type="checkbox">` with label wrapping; flag cards → buttons with `aria-pressed`.
3. Every ✕ → `aria-label="Close"` / `"Remove hazard"` etc.
4. Modal containers → `role="dialog" aria-modal="true" aria-label="…"` (combine with W5 focus work).
5. Quick pass with axe DevTools; fix contrast flags if any (palette is mostly compliant; check `#C8C2B8` on `#FEFEFC` small text — likely fails AA, bump to `#8C887E` where it's meaningful text).
**Accept:** Whole wizard completable with keyboard only; toggles flip with Space; axe reports no critical issues on Dashboard/Editor/Wizard.

### F5 — QR code on share links

### F6 — Editor autosave drafts

### F7 — List search should cover hazard text
RAList search currently matches name/ref/location only. Users ask "which RA covers ladders?" — include `hazards[].hazard` in the search haystack (join once per RA, memoised).

### F8 — "Last synced" indicator + manual refresh
Small nav footer text: "Data loaded 09:42 · ↻". Reassures multi-device users (vicar's iPad vs office PC) that they're looking at current data; the refresh re-runs `loadAll` without a full reload.

### F9 — PWA update prompt
`registerType: 'autoUpdate'` still leaves a stale tab running old code until reload. Use `vite-plugin-pwa`'s `useRegisterSW` hook to show "New version available — Refresh" — removes the whole `?nocache=1` support-question class.
